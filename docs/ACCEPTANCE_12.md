## 2. FINDING 1 — step-1 prepare 502s on the owner's document (measured-not-fixed, out of #48 scope)

The SPA's bare upload path (`files` + `simulation_requirement`, exactly what
`frontend/src/views/Process.vue` sends) **fails on this document with the `small`
model**:

```
[prepare] attempt 1/6 FAILED (bare SPA field set, 502):
    LLM JSON output was truncated at the token limit   project_id=proj_c19339a99976
```
(`scratch/accept48_run_1794104337.log`; the same 502 was re-measured on the
previous attempt of this run, `accept48_run_1794101855.log`, project
`proj_2d857b5ed29b`.)

**Cause chain (all shipped values, no code changed):**

1. `OntologyGenerator.generate` passes `max_tokens=None` ("let the provider use
   its model-specific limit", `app/services/ontology_generator.py:241`).
2. `MLXRunner.generate` only forwards a truthy `max_tokens`
   (`app/models/runtime.py:267`), so the kwarg is **dropped**.
3. mlx-vlm therefore applies its own **`DEFAULT_MAX_TOKENS = 2048`**
   (`mlx_vlm/generate/common.py:22`).
4. The 1.7B's ontology JSON runs past 2048 tokens → `finish_reason=length` →
   `LLMClient._parse_json_response` raises `LLMResponseError` → the endpoint
   answers **502**. The backend log line proves the retry was byte-identical
   (`LLM returned unusable JSON (finish_reason=length); retrying content
   generation` — *without* the "without an output token cap" suffix, i.e. the cap
   was already `None`), so `max_attempts=2` truncates twice.
5. Context, not the cause: the same prompt measures **17,189 tokens** (system
   1,391 + user 15,798, measured with the model's own tokenizer over the saved
   `extracted_text.txt`) against `LLM_CONTEXT_LENGTH=8192`. MLX tolerates the
   over-length prefill, so this is recorded for completeness only.

**Known model behaviour, not a new class:** the 1.7B's verbosity is the same
property that produces the `ExtractedEdges` clamp class in `docs/MODEL_EVAL.md`
§7c item 10; here it overruns a 2048-token output budget instead of a 4096 one.

**Owner-approved workaround (this run):** the same real endpoint was called once
with one user-typable extra field — `additional_context`, asking for a compact
ontology (≤1 attribute per type, no `examples`, exactly 6 edge types, short
`analysis_summary`) — and it succeeded on attempt 2/6 (43 s):

```
[ok] prepare succeeded on attempt 2/6 (additional_context compact-ontology constraint);
     project_id=proj_f3de02128caa
```

**Status: measured-not-fixed, out of #48 scope.** The fix belongs to the
step-1 prepare path (an output-token budget for the local runner, or a shorter
prompt), not to this acceptance run; nothing in `.env` or the registry was
touched to mask it. Recorded here as an open item for the owner in the style of
#24 (measured-not-fixed).

## 6. Findings recorded (no app-code changes made)

1. **Step-1 prepare 502s on the owner's document with `small`** (§2) —
   measured-not-fixed, out of #48 scope; open item for the owner.
2. **`record["skipped"]` / `record["skipped_indices"]` overcount after a resume.**
   `_ingest_record` re-attempts every item that is not `succeeded`, so a skipped
   chunk does get a genuine second chance, but the counters are monotonic: a
   re-skip appends the index again and a flip back to `succeeded` never
   decrements. Measured: counter `skipped=47`, `skipped_indices=[0,1,2,5,6,0,2,6,…]`
   while the item statuses show **42** skipped. `_wait_for_batch`'s gate reads the
   *item statuses* (correct), but the terminal task result's `skipped` /
   `skipped_indices` come from the inflated counter. The authoritative per-chunk
   status is the batch record's `items[]`.
3. **The §8 resume endpoint re-wraps the build response** — the new task id is at
   `data.data.task_id`, not `data.task_id` (`resume_session` returns
   `{"session_id": …, "resumed": true, **build_payload}`). Cosmetic, but it
   cost this run's first attempt its instrumentation; recorded, not fixed.
4. **The 30% skip-fraction guard failed the task on a 79% measured rate** (§4) —
   the shipped behaviour, recorded as the acceptance outcome rather than
   suppressed.
5. **Shutdown-path note:** the atexit unload at the end of the run logs
   `model … unload error: cannot schedule new futures after shutdown` and
   `MODEL UNLOADED … rss_before=2137MB rss_after=2137MB` — the footprint does not
   release during teardown because the runtime is already closing (the same
   pattern in the earlier attempt). Harmless at process exit; recorded only.
